# The lossless encoder, and how far it has got

[`hz-mlp`](../crates/hz-mlp) writes TrueHD. This is the notebook: what was
tried, what it measured, and what was put down again. For the state of the
encoder as it stands — every constant and decision in force, with no history —
see [`mlp-state.md`](mlp-state.md).

## Where it stands

**`decode(encode(x)) == x`, bit for bit**, across every shape the encoder
accepts — mono, stereo, 5.1, 7.1 and **sixteen elements over four
substreams**; 16- and 24-bit; 44.1 / 48 / 88.2 / 96 / 176.4 / 192 kHz; and
lengths that are not a whole number of access units:

```bash
cargo xtask mlp programme.wav --out programme.thd
```

The check runs through **two decoders that share no code with this or with each
other** — FFmpeg's and `harletty`'s, the maintained line of `truehdd` — and
through **every presentation the stream declares**, not only the widest,
because a decoder may stop after any of them and that is what the substream
split is for. A sixteen-channel stream is therefore checked four times over:
two channels, six, eight, sixteen. The harness runs whatever `HARLETTY` names
(`TRUEHDD` is still honoured), else `harletty` on the path.

That last paragraph used to be half true, and the half that was missing cost
weeks of a wrong encoder looking right. See
[what one decoder cannot tell you](#what-one-decoder-cannot-tell-you).

## How big the streams are

Against FFmpeg's encoder, which is the only encoder available to compare
against — the reference engine cannot be used without a licensed run of it,
and none has been available (see [LEGAL.md §3.1](../LEGAL.md)).

|---|---|---|---|---|
| A programme's centre channel, 40 s | 5.82 MB | 4.18 MB | 4.03 MB | **0.96×** |
| A programme in stereo, 40 s | 11.6 MB | 7.77 MB | 7.34 MB | **0.94×** |
| The same programme in 5.1, 40 s | 34.9 MB | 18.0 MB | 17.5 MB | **0.97×** |
| Independent pink noise, stereo | 2.30 MB | 2.18 MB | 2.08 MB | **0.96×** |

| The same programme in 7.1, 40 s | 46.6 MB | — | 18.7 MB | — |

Uncompressed, the programme row was 2.04×, and the table read 1.09× to 1.12× on
real material until the dead bits, the kept filters, the restart interval and
the silent channel parameters were dealt with, in that order. Under FFmpeg's
encoder on every row now, by two to six per cent.

Against the reference stream — the comparison that matters, see
[encode.md](encode.md) — a thirty-second slice re-encoded is **1.0035×** the
size: 13 491 770 bytes against 13 444 136, or 0.02 bit a sample.

The last two rows have no comparison because **FFmpeg's encoder does not write
those shapes**: handed 7.1 or sixteen channels it downmixes to 5.1 and writes
that instead. Above six channels this encoder is on its own, with the decoders
and the reference stream as its only checks.

**A warning about stereo fixtures.** The stereo test files first used here were
generated by `anoisesrc` and turned out to be **dual mono** — the same samples
in both channels. Rematrixing scored a 50 % gain against them, which was a
measurement of the fixture and not of the encoder. Everything above uses
material whose channels genuinely differ.

## What one decoder cannot tell you

The acceptance criterion for this phase has always said two decoders, "so a
shared bug in one cannot hide". For a long time the harness ran the round trip
through FFmpeg and only asked `truehdd` whether the framing parsed. Running
both properly found this on the first try:

**A restart header wipes the decoder's filter state, and the two decoders
disagree about it.** `truehdd` clears every byte of its substream state at a
restart. FFmpeg leaves its state buffers alone. Neither is unreasonable, and
the difference is invisible for a stream that never restarts — but this one
restarts every sixteen access units, and it was carrying its own history across
each one. FFmpeg agreed with it exactly. `truehdd` began a slowly decaying
error at every restart but the first, because the reconstruction is recursive
and a wrong initial state rings out through it: the error at the restart was
about half the sample value and fell by 0.56 % a sample.

Which of them is right is not a matter of taste. A restart header is where a
decoder may **join** the stream — that is the only reason to spend thirty bytes
on one — so nothing after it may depend on what came before. `truehdd` is
right, and a stream that needs FFmpeg's leniency is a stream that cannot be
seeked into.

The fix is not "reset the encoder's history": that satisfies `truehdd` and
breaks FFmpeg, which would still predict from the state it kept. The state has
to stop mattering, and the format says how. **After a restart header a
decoder's block size is eight and its filter orders are zero** — and eight is
exactly the longest filter this format has. So a restarting access unit is
written as *two* blocks: eight samples with no prediction at all, which refill
the state from their own data and are identical whatever a decoder did with the
state before them, and then the remaining thirty-two with filters on, predicted
from a state both decoders now agree about.

It costs almost nothing. Three ways of fixing it, measured on a programme in
stereo:

| | Ratio of raw | Correct in |
|---|---|---|
| Carry the history across the restart | 0.724× | FFmpeg only |
| Code the whole restarting unit unpredicted | 0.744× | both |
| **Eight unpredicted samples, then the rest** | **0.725×** | **both** |

A tenth of a per cent for a stream that is right in both decoders and can
actually be joined at a restart.

There is a second, harmless disagreement in the same area: the end-of-stream
marker. FFmpeg truncates the last access unit to the length it states;
`truehdd` reads the same field as "how much of this unit is silence" and hands
the padding back. Both are right about the samples, and the harness says so
rather than reporting a mismatch.

## Prediction

Two things had to be true at once. The coefficients are chosen in floating
point, by autocorrelation and Levinson-Durbin over the last 256 samples plus
the block in hand; but once they are integers, the filter is run in exactly the
decoder's arithmetic — 64-bit accumulator, arithmetic shift, in that order —
because a predictor that rounds differently at either end is not lossless.
[`filter.rs`](../crates/hz-mlp/src/filter.rs) does the second half and its test
reconstructs the samples through a separately written copy of the decoder's
loop, so a mistake would have to be made twice, in opposite directions.

Every order from one to eight is tried and the residuals actually computed,
rather than the order being picked from the prediction error the fit reports.
Those are different questions. The fit's error is a statistic about a windowed,
real-valued model; what this coding pays for is the **largest** residual in the
block, because that sets the field width every sample in it is written at.

Two measurements shaped it:

- **The fit needs more than the block.** Fitting on the forty samples in hand
  plus eight of history left a pure tone at 13.4 bits a sample, where the
  coefficient precision alone should have allowed far fewer: an eight-tap fit
  has eight unknowns, and forty-eight samples is not much to pin them with.
  Fitting over 256 samples of context brought it to 10.5. Beyond 256 nothing
  changed, and 512 cost twice the arithmetic for an identical answer.
- **The framing was the bigger cost.** With prediction in and a restart header
  in every access unit, framing was **45 %** of the stream on real material —
  more than the residuals. Restarting every sixteenth unit instead took the
  programme row from 1.16× FFmpeg's size to 0.80× of raw, and framing to 21 %.

## Entropy coding

A residual's low bits go on the wire as they are; what is left above them is a
small number, and one of three codebooks prices *that* — short codes near zero,
long ones at the edges. All three spend the same codes on the outer values and
differ only in the middle: one gives a single bit to one value, another spreads
three-bit codes across four. So choosing between them is choosing how peaked
this block's residuals are, and it is done per block by costing all of them.

It is worth about half a bit a sample. That sounds thin, and it is the right
order: the tables hold fifteen to eighteen symbols and only price the top of
each residual, so they are not a general entropy coder and cannot reach the
Laplacian bound. Where they earn is at the extremes — a block of digital
silence now costs **nothing at all**, because no codebook and no low bits is a
legal coding whose only representable value is zero.

What gets chosen, on a programme's centre channel: codebook 1 for 61 % of
blocks, codebook 2 for 33 %, codebook 3 for 2 %, and no codebook for the
remaining 4 %.

### The offset field is not used, and that is a measurement

The format also carries a fifteen-bit offset that slides a codebook's window
along the number line, which would let a block the filter left slightly biased
fit a window one bit narrower. It was implemented, and it made the programme's
stream **larger** — 4 542 740 bytes against 4 541 984 — for twenty per cent
more encoding time. That is what "prediction residuals are close to zero-mean"
looks like from the other side: the window is already where it belongs, and
moving it costs fifteen bits that a narrower field does not repay over forty
samples. Removed. The offset stays in [`huffman`](../crates/hz-mlp/src/huffman.rs),
which is where the format defines it and where a later tool with biased
residuals might want it.

## Rematrixing, and what it turned out to be worth

Two channels of a mix are usually more alike than either is like silence, and
prediction within a channel cannot see that. The format's answer is a
*primitive matrix*: one channel is replaced by itself minus a weighted copy of
another, and the decoder puts it back. It is exactly invertible because the
destination's own coefficient is one in fourteen fractional bits, and
`(2¹⁴·a + b) >> 14` is exactly `a + (b >> 14)` — no rounding survives the round
trip.

Both directions are tried, with a least-squares weight, and costed exactly
against coding the channels separately. What that costing says:

| Material | Access units matrixed | Gain |
|---|---|---|
| A programme in stereo | **0 %** | **none** |
| Independent noise, stereo | 0 % | none |
| Correlated noise, stereo | 81 % | 2.4 % |
| A sine, identical channels | 100 % | 42.9 % |

**On a real programme's stereo downmix it is worth nothing, and the search
declines it every time.** That is not a bug and it was checked: forcing the
matrix on regardless makes that stream *larger* — 0.766× against 0.724×. A
programme's stereo mix is a fold of a multichannel one; its two channels share
the centre and differ everywhere else, and one scalar weight is not a model of
that.

Where it does pay it pays properly, and the search tells the cases apart, which
is the property that matters. Two decisions made it pay more than it first did:

- **The matrix is decided once per restart interval and held**, not chosen per
  access unit. It costs forty-odd bits to describe, worth amortising over
  sixteen units — but the real reason is that switching it turns the signal a
  channel carries into a different signal, which the prediction filter's
  carried history and fit context are then wrong about for a quarter of a
  second. Holding it doubled the gain on correlated noise, from 0.6 % to 2.2 %.
- **The weight is estimated from a thousand past samples**, not from the forty
  in hand. Same lesson as the filter's fit context, and the weight is a single
  number, so more data costs almost nothing.

## The second prediction filter, which pays after all

The format carries two filters per channel. The first predicts the next sample
from past samples; the second predicts it from past prediction *errors*.
Together they are an ARMA predictor whose error filter is `(1 − A)/(1 + B)`:
the first places zeroes, the second places poles.

**Fitted to what the first filter leaves, it never paid.** That was measured,
charged honestly, and the streams came back byte-identical to having no search
at all: after an eight-tap fit over three hundred samples, what is left is the
coefficients' quantisation error, which is white, and no model of past
residuals predicts white noise. That verdict stands. FFmpeg's encoder does not
use this filter either.

**What it is for is something else.** Read from a shipped stream with
`harletty info --filters`, the second filter is nearly the same on every
channel and in every block: about `[1.72, 0.77]` at order two and `0.83` at
order one, with 6+2 and 7+1 the common pairs. Those are two poles near Nyquist
on the whitening filter — a fixed design, not a fit. Programme audio has a steep
low-pass roll-off, and a valley that deep is what zeros model badly and two
poles model cheaply. Measured offline on this project's fixtures, with the
first filter fitted to the pre-filtered signal `x / (1 + B)`: 0.10 to 0.19 bit
a sample off the residual width, on every one of them.

So the encoder carries three fixed second filters — `0.83`, `[1.5, 0.6]` and
`[1.8, 0.85]`, the best three of a grid over three fixtures — with the first
filter fitted to what each leaves. Four things had to be right before the
gain showed, and each was measured:

- **A second filter has to be started with a history.** Its taps run over
  past residuals, and the residuals the decoder holds were made by whatever
  filter came before; with poles at 0.9 that error poisons a whole block, so
  a pair evaluated from the decoder's real history lost the very block it
  would have entered on. The format has the answer: a filter may carry a
  *state block*, its history written with the taps, allowed on the second
  filter only — and the shipped stream sends one with every second filter it
  starts. The encoder runs the pair over the last sixty-four samples to find
  the history it would have left, installs that, and evaluates the block from
  it; whichever of the two evaluations is cheaper wins.
- **A candidate is charged for what it will write.** The second filter's
  description was being charged to every pair, in force or not — ten bits a
  block held against it.
- **It is decided once per interval, not once per block.** A second filter is
  a design that stays on for as long as the signal keeps its roll-off, so it
  is decided where the matrices are, at each restart, per channel; within the
  interval the block chooses only the first filter, and a pair that continues
  is the same filter whatever shift its taps were quantised at. Block by
  block, the search never entered a pair on a quiet channel — its whole
  description is a third of such a block and its gain a few bits — and when
  its description was charged lightly enough to enter, it churned between
  designs and state blocks that the light charge could not see, and the
  streams grew.
- **And no model of the residuals' width will do as the judge.** The offline
  model that promised the gain fitted its predictors through a flat window
  and measured the width the residuals need; the encoder fits through a Welch
  window, and on a 296-sample fit that is worth over a bit a sample to the
  first filter alone — the model was degrading the baseline, not improving
  the pair. Judged that way, a flat-windowed model put the pair on every
  quiet channel and lost 1.5 % there; a Welch-windowed one found a twelfth of
  what a programme channel actually saves. The judge is therefore the block
  search itself: at each restart the last forty-four blocks of the channel's
  coded past are coded again in every mode, with the exact costs, and the
  cheapest mode is carried. (A flat window in the block search itself, tried
  while at it, costs 2 % everywhere: the window is right where it was.)

| Fixture | Before | After | |
|---|---|---|---|
| A programme's centre channel, 40 s | 4 080 660 | **4 026 892** | −1.3 % |
| A programme in stereo, 40 s | 7 416 738 | **7 338 278** | −1.1 % |
| The same programme in 5.1 | 17 663 838 | **17 485 298** | −1.0 % |
| The same programme in 7.1 | 18 890 164 | **18 749 872** | −0.7 % |
| A programme's twelve elements, 10 s | 3 819 002 | **3 791 638** | −0.7 % |
| The same programme, eight elements | 3 318 110 | **3 287 544** | −0.9 % |
| A busy sixteen | 3 632 520 | **3 584 192** | −1.3 % |
| A sparse bed | 548 432 | **540 602** | −1.4 % |
| A localisation test | 2 165 738 | **2 145 548** | −0.9 % |
| Correlated noise, sixteen | 2 251 880 | 2 253 284 | +0.06 % |

Every fixture bit exact through both decoders and every presentation, and the
programme slice of [encode.md](encode.md) goes from 1.013× the reference stream
to **1.0035×** — 13 491 770 bytes against 13 444 136, 0.02 bit a sample. The
second filter is taken in 40–79 % of blocks on real material, against 65–88 %
in the reference. On a quiet element alone the gain is a fifth of a per cent,
and that is not a shortfall: coded exactly, the pair is worth little there,
whatever a width model says. The search costs time — the trial codes
forty-four blocks four ways per channel per interval — and the programme slice
encodes in thirteen seconds where it took four. **`--fast`** tries one design,
the order-two one that is taken most often, and only at every other restart,
keeping the channel's decision in between: the programme slice comes out at
13 526 670 bytes, 1.006× the reference, in six seconds; on the fixtures it
gives up a tenth or two of a per cent on real material and half a per cent
on the synthetic sixteens, for about half the time. Two of the time's four
seconds are what the pair costs the block search itself.

### How often the stream restarts

Every 128 access units, which is the most the format allows: a decoder refuses
a wider gap by name, and a reference stream sits right at the cap.

It was 16 for most of this encoder's life. Moving it to 128 was measured once
and found to be worth **1.5 %**, which is not where anyone would spend an
afternoon. After the filters stopped being restated, the dead bits stopped
being coded and the matrix search widened, the same change is worth **5.3 %** —
the stream around it got forty per cent smaller and the framing did not.

| Fixture | Every 16 | Every 128 |
|---|---|---|
| A programme's twelve elements | 4 149 798 | **3 930 726** |
| A sparse bed | 753 130 | **642 136** |
| Correlated noise | 2 624 480 | **2 438 698** |
| A programme in stereo | 7 751 648 | **7 470 246** |

A lever measured once and put down is worth picking up again when everything
around it has changed.

### Which channels get coded against which

A matrix codes one channel as a difference from another, and this used to try
only **adjacent pairs**: channels 0 and 1, then 2 and 3, and so on. That is six
of the sixty-six a twelve-element programme has, and the pairs a programme
correlates are not the ones that happen to sit next to each other. In a
programme measured for this, the two that matter are elements three and eight
— never tried, correlated at 0.997.

So every channel now looks for a partner among everything its substream has
already decoded, choosing by correlation over the interval just gone, which is
cheap, and then costing that one candidate properly, which is not.

| Fixture | Before | After |
|---|---|---|
| Correlated noise | 16 140 448 | **2 624 480** |
| A sparse bed | 3 504 546 | **753 130** |
| A busy sixteen | 4 814 694 | **3 819 492** |
| A programme's twelve elements | 4 321 098 | 4 149 798 |
| A programme in stereo | 7 744 672 | 7 751 648 |

The large numbers are fixtures built to correlate and the small ones are
programmes, which is the honest way round: a programme's objects mostly are not
each other. Four per cent of a programme slice, and it goes from 1.12× the size
of the reference stream to **1.09×**. A stereo file pays 0.1 % for a search
that finds nothing new in two channels.

**A matrix costs one description per substream that has to undo it**, so where
its destination sits decides what it has to earn: one on the stereo pair is
written four times, one on the last substream once. Which is why a reference
stream permutes its channels — its assignment is `[3, 1, 6, 9, 8, 0, 7, 2, 10,
11, 4, 5]` where this writes the identity — and why reordering a programme's
elements to put the correlated pair at the *bottom* made things worse before
this went in. It is also why permuting is not needed: the destination decides
the cost, and a destination in the last substream may take its source
anywhere.

**One direction, chosen by the caller.** Trying both — which was safe while the
pairs were always inside one substream — writes a matrix whose source the
substream declaring it has not decoded. It parses, every checksum verifies, and
a decoder stopping at the six-channel presentation hands back channel four
still matrixed. Both decoders caught it at the second restart interval.

**Chains are allowed.** A source may itself be a matrix's destination; the
matrices are a list applied in order and undone in the same order. Forbidding
that, which looked tidier, cost a sparse bed 167 % of its size — the whole
point of such a bed being that many of its channels come from one.

### The bits that were never there

A programme's elements arrive as twenty-four-bit samples whose bottom four bits
are always zero — twenty bits of content in a twenty-four-bit container. Coding
the zeroes underneath costs four bits a sample, and for a while this encoder
paid them: 11.2 bits a sample where FLAC managed 6.44 on the same file and the
reference stream 6.20.

The format has the field. `output_shift`, four bits and signed, per channel in
the block header, bounded by `max_shift` in the restart header — which this
wrote as zero, meaning nothing may be shifted. A decoder applies it at the very
end, after the filters and after the matrices, so taking the bits off costs the
prediction nothing.

| Fixture | Before | After |
|---|---|---|
| A programme's eight loudest elements | 5 572 982 | **3 694 612** |
| The same programme, sixteen elements | 6 932 966 | **4 396 466** |
| A programme in stereo | 7 744 672 | 7 744 672 |
| Correlated noise, a bed, a busy sixteen | — | byte-identical |

A third off where the content is narrower than its container, and *byte*
identical where it is not: a stream whose samples fill their width says nothing
about shifts, because a restart header leaves a decoder holding zeroes and
there is nothing to correct. A whole programme slice goes from 1.70× the size
of the reference stream to **1.12×**.

**The order is the whole of it.** A decoder runs filter, then matrix, then
shift; so an encoder must shift, then matrix, then filter. Shifting after the
matrices instead — which is where this went first — produces a stream whose
first second is exact and whose 48000th frame is not, with every checksum
verifying. Both decoders caught it and agreed on the frame.

**Silence asks for nothing.** Zero is divisible by every power of two, so a
silent block claims the largest shift there is and hands it back at the next
block with content in it. Each change costs a declaration and unsettles the
coded domain the filters predict in, so a block with nothing in it holds
whatever shift is already in force.

### How many elements an object programme has

Twelve, fourteen or sixteen in the reference streams, and the description does
not change between them: same `substream_info`, same extension, same three bed
substreams.
Only the fourth substream's range moves — it ends at channel 11 in a stream of
twelve elements and at 15 in one of sixteen.

So this writes any count from nine, which is the fewest that leaves the fourth
substream anything to carry, to sixteen. Nine to sixteen all round-trip bit
exactly through both decoders at all four presentations, including the odd
counts, which no shipped stream uses and nothing in the syntax distinguishes.

### What did pay, later: keeping the first filter

The verdict above stands for the *second* filter and this one is about the
first, but they were confused for a while, so it is worth being plain: the
gap between this encoder's streams and a reference one's was blamed on the
missing second filter, and it was not that.

Both filters have a presence bit, and until now only the second one used it —
the first was restated in every access unit, unconditionally. On a forty-sample
block an order-four description costs about as much as it saves, so the search
kept choosing orders one and two, and the streams paid for shallow filters over
and over. Letting a block say *nothing* about a filter it is happy with, and
pricing the one already in force at zero, changes what the search will accept:

| Fixture | Before | After |
|---|---|---|
| A programme's eight loudest elements | 6 194 792 | **5 572 982** |
| The same programme, sixteen elements | 7 590 298 | **6 932 966** |
| A programme in stereo | 8 464 008 | **7 744 672** |
| Correlated noise | 16 496 660 | **16 140 448** |
| A sparse bed | 3 832 988 | **3 504 546** |
| A busy sixteen | 5 333 736 | **4 814 694** |

Between 2 % and 10 %, every fixture, and the filter orders chosen move from
"one and two, 87 % of blocks" to a spread centred on four. A whole programme
slice goes from 1.88× the size of the reference stream to 1.72×.

**A block is charged a quarter of a filter's description.** Not the whole of
it, because a filter is described once and kept until it stops paying, so
charging one block the lot prices it as if it lived for one block. The quarter
is measured and not derived: it is the best of 1, 2, 4 and 8 across four
fixtures, and eight does better on three of them and half a percent worse on
the fourth, which is why it is not eight. This is the kind of constant that
should be re-measured when anything else here changes.

**And filters become sticky.** With switching priced in full they were restated
in under 1 % of blocks — kept for hundreds — which is a filter fitted once and
then left to go stale. The quarter is also what stops that.

The *fitted* search for a second filter is gone; what replaced it is in
[the section above](#the-second-prediction-filter-which-pays-after-all).

Two things did come out of the first attempt:

- **The filter shift must be at least eight**, which one of the two decoders
  rejects a stream for and the other does not check. Now enforced: a predictor
  whose coefficients are too large to represent at eight fractional bits is
  not offered rather than clamped into something that decodes differently. It
  changed no output — every shift already satisfied it — which is the good
  outcome for a constraint discovered late.
- **"Unchanged" has to mean unchanged.** Saying a filter had not changed
  because its *order* had not, while its coefficients had, produced a stream
  that decoded to the wrong samples with every checksum intact. Only the round
  trip caught it, which is the argument for having one.

### And then a channel that says nothing at all

One level up in the syntax there is the same shape again. Every channel in
every block carries one bit saying whether its parameters follow — the two
filters' own presence bits, the offset's, the codebook and the width — and this
encoder set it in every block, unconditionally, then said "unchanged" for the
filters and restated the codebook and width. A channel whose coding is exactly
what the decoder already holds was therefore costing eleven bits a block for
nothing, and on the programme's twelve elements **62 % of channel-blocks were
exactly that**.

A decoder that reads a zero keeps everything it holds for the channel — FFmpeg's
and `truehdd`'s both — and a restart header clears all of it back to no filter,
no codebook and twenty-four bits. So "nothing" is right only between restarts,
which is the rule the filters already follow: the encoder now remembers the
codebook and width it last wrote beside the filters it last wrote, and a channel
says something only when one of them differs.

restating that in every block; it now costs one bit a block, and a sparse
sixteen-element stream is mostly silent channels. The harness prints how many
channel-blocks say anything — 38 % on the programme's twelve elements, 4 % on
the localisation test.

## More than two channels

Past two channels TrueHD splits the stream: substream 0 carries a stereo
presentation a two-channel decoder can stop after, substream 1 carries the
rest. They share one buffer of channels, which is why substream 1's matrices
may reach back over substream 0's.

5.1 and 7.1 both round-trip bit-exactly. Three things had to be right, and two
of them are invisible in a bitstream that parses cleanly:

**A full decode applies the matrices of the last substream and of no other.**
So a matrix on the stereo pair has to be declared *twice*: in substream 0, for
a decoder that stops there, and again in substream 1, for one that does not.
Declared only in substream 0, it parses, every checksum verifies, and whole
restart intervals of the stereo pair come back still matrixed because nothing
undid them. It took a bisection by feature to find, because with the filters
and codebooks turned off the residuals were visibly small where the samples
were large — a matrix had been applied and not removed.

**Past six matrix channels the noise-type bit must be set.** It is the bottom
bit of the restart header's sync word: `0x31ea` clears it, `0x31eb` sets it,
and FFmpeg's encoder has a `TODO 0x31eb` exactly there — which is why its
TrueHD encoder stops at six channels. Setting it also changes what a matrix
looks like: the two synthetic noise channels leave its source list, and each
matrix gains a noise shift.

**The channel order is not the WAV order.** The format's is the order of the
arrangement's groups — left and right, centre, low frequency, *side*
surrounds, then rear. A WAV file's is the order of its channel mask, which puts
the rears first. They agree up to 5.1 and disagree at 7.1, and an encoder that
ignores the difference produces a stream whose surrounds are swapped and whose
every check passes.

Rematrixing finds nothing to do on the 5.1 material either — 0 % of access
units, the same answer it gave for stereo, and for the same reason.

## Reading, and the immersive stream this is measured against

`cargo xtask thd stream.thd` reads an access unit's *structure* — the header,
the major sync, the substream directory, the restart headers — and checks every
checksum. It is not a decoder; it stops where the block data starts, which is
exactly the part an encoder has to get right and exactly the part that fails
silently when it is wrong.

It exists because phase A2 needs what phase A1 had: **a real stream to hold
things next to**. There is one — an immersive localisation test in TrueHD —
and reading it maps the whole immersive layout:

| | The reference | What this writes today |
|---|---|---|
| Substreams | 4 | **4** |
| Presentations | 2ch, 6ch, 8ch, 16 elements | **all four** |
| Major sync | 32 bytes — an extra channel-meaning block | **32** |
| `substream_info` | `0xfc`, extended `0x3` | **the same** |
| Declared peak | 663 (≈2 Mbit/s) | 5999 (18, the ceiling) |
| Flags | `0x1000` | **`0x1000`** |
| Directory entries | 4 bytes — a second word of dynamic range control | **4, on request** |
| Rematrixing | yes, in every substream | **yes, in all three syntaxes** |
| Extra data | 78 bytes a unit — the object metadata | **the block, not yet the metadata** |

Its four substreams are `0..1`, `2..5`, `6..7`, `8..15`: each presentation adds
to the one before it. Three details of that are not guessable:

- **The restart sync word is not one value.** `0x31ea` and `0x31ec` both occur,
  and the reference uses `0x31ea`, `0x31eb` and `0x31ec` across its four
  substreams. FFmpeg's decoder reads thirteen bits of sync and a noise-type
  flag, so it accepts only the first pair — which is another way of saying it
  cannot read the sixteen-element presentation.
- **The channel assignment is a permutation**, not the identity this encoder
  writes: `[0, 3, 2, 5, 1, 4]` for the 5.1 presentation. That is how one buffer
  of channels serves four presentations at once.
- **The major sync's length is read from inside itself** before anything is
  parsed, and an Atmos stream's is longer. A reader that assumes 28 bytes lands
  in the middle of the substream directory and produces entries that look
  plausible and are nonsense. That is what happened first.

One thing in the reference is still unexplained: **bit 12 of the first
substream's directory entry is set**, and clear in the other three. Both
decoders skip that bit without naming it. It is written clear here, which is
what they expect; it is recorded because a field nobody reads is exactly the
kind that turns out to matter.

Every checksum in that stream verifies against this project's implementations —
the major sync over a 32-byte header it had never seen, and the restart header's
bit-range checksum over four differently shaped substreams. That is a stronger
confirmation of `crc.rs` than anything written here could be.

## Four substreams

A sixteen-channel stream is written and every one of its four presentations
decodes bit-exactly. What that took, beyond the split itself:

**The restart sync word is a three-valued field, not a sync plus a flag.** A is
substream 0's, B is substream 1's and 2's, C belongs to substream 3 and to
nothing else — and a decoder enforces all three of those. They select three
different matrix syntaxes, which is why reading the low bit as a "noise type"
works for two of them and produces nonsense for the third.

**The extra channel meaning says what the sixteen elements are**, and it is
what makes an immersive major sync 32 bytes rather than 28. The reference
declares fifteen dynamic objects and a low frequency channel, dialogue
normalisation −31 dB and a mix level of 105 dB; this writes the same shape.
Both are read back by `cargo xtask thd`, so the field is checked against a real
stream rather than asserted.

**The peak bitrate has a ceiling, and sixteen channels are above it.** A
decoder multiplies the field back out and refuses anything over 18 Mbit/s.
Sixteen channels of 24-bit audio at 48 kHz are 18.4 Mbit/s uncompressed — so
the format *requires* an immersive stream to compress, and an encoder that
could not would have nothing legal to declare. The encoder declares whichever
is smallest of the nominal figure, what its coding can produce, and that
ceiling, and the harness **fails** when a stream overruns what it declared: the
samples may still come back exactly, which is precisely why it cannot be a
remark.

It is reachable — sixteen channels of correlated pink noise peak at
18.5 Mbit/s — and the answer is that **a unit does not have to fit on its own**.

## The arrival clock is a schedule

An access unit's bytes are delivered over the gap between its own arrival time
and the next one's, so a unit larger than the average is given a longer gap and
the units after it are given shorter ones. The peak constrains a *rate*, and a
rate has a denominator.

The rule, read out of the reference stream rather than guessed: the gap after a
unit is at least `ceil(length in words × 256 / the declared peak field)`.
Checked over its first 25876 access units, **it is never once short of that**,
and the gaps run from 17 samples to 129 against a frame of 40 — while their mean
is **40.002**. The two clocks keep the same average rate, which is the other half
of the rule: a stream whose clocks drift apart is one whose buffer eventually
empties.

What is borrowed has to come from somewhere, so a stream gives itself a reserve
at the start — the reference gives itself 60 samples, and its buffer then swings
between −60 and +113 of where it began. This gives itself eight access units,
under seven milliseconds, an order inside the seventy-five the format allows.

With that, the stream that could not be written before round-trips bit-exactly
through every one of its four presentations, with no complaint from the decoder,
and its buffer never drops below 318 of its 320 samples. Nothing else changed:
a stream whose units all fit gets the nominal gap every time, and every fixture
comes out as it did.

🔴 **What a schedule cannot fix** is a stream that needs more than it declared
*on average* rather than in one unit. That is not a peak, it is a bitrate, and
the encoder now reports it as units it could not place rather than as a unit
that was too big.

**The gap is sized from the unit just written, not the one before it.** Sizing
it from the one before satisfies the mean, varies the gaps, and looks entirely
correct — and drew 154 complaints from the decoder over two seconds of audio.

**Rematrixing is all or nothing across an immersive stream.** A decoder undoes
the matrices of the substream it stops at and of no other, so every
presentation has to be able to undo everything under it. Declaring matrices
only in the substreams whose syntax you happen to have implemented would parse,
verify every checksum, and hand back a sixteen-element mix that is still
matrixed. So sync word C's syntax had to be written before an immersive stream
could carry a matrix at all — see below.

## Sync word C's matrices

The third syntax, and the reason an immersive stream could not rematrix until
it was written. Four things are said differently, and one thing is said that
the other two syntaxes cannot say:

- Which coefficients are present is a **mask** written up front, one bit per
  source, rather than a presence bit before each coefficient. The same bits in
  another order, and the coefficients follow in a second pass over the
  matrices rather than interleaved with their descriptions.
- The count is written as **one less than itself**, so this syntax cannot
  express "no matrices" that way at all. It says so with a leading bit
  instead — and that bit also lets a later block re-send coefficients without
  re-sending the configuration.
- Each matrix carries a **shift applied to the whole of it**, `2^n` on every
  coefficient at once, on top of its fractional bits.
- And a second set of coefficients may be given that the first **interpolates
  towards** across the access unit, so a matrix can move while a block is
  decoded — and, at the end of the unit, the whole step is *added* to the
  coefficient, so one statement tracks a trend for as long as the matrix
  stands. See below.

With the shift at zero and no dither the arithmetic reduces to the other
syntaxes' exactly — accumulate, shift down by the fractional bits — so one
`Primitive` describes a matrix for all three and only the writing differs.

What it is worth, on sixteen channels whose elements are correlated, which is
what a bed and objects derived from it look like:

| | Bytes | Rematrixed |
|---|---|---|
| Without | 6 308 594 | — |
| **With** | **3 832 988** | 100 % of units |

**−39 %**, and all four presentations still bit-exact. On material whose
elements are *not* correlated it is declined and costs nothing: the localisation
test and the 7.1-plus-its-reverse fixture both come out byte for byte as they
did before.

**Pricing a matrix now prices what is written.** The decision costs a candidate
by encoding it, and a matrix is only ever chosen in a unit that restarts — which
since the [restart block](#what-one-decoder-cannot-tell-you) is two blocks, not
one. Three estimators were measured over six fixtures: this one, pricing the
unit as a single block from a zero state, and pricing it as a single block from
the state a *typical* unit of the interval carries. Pricing what is written wins
or ties on five of the six, by up to 3.6 kB; the zero-state one wins on a
programme in stereo by 680 bytes.

## The directory's second word

A substream directory entry is two bytes, or four if it carries a **dynamic
range gain** for that presentation. It is metadata and not coding: a decoder
asked for full dynamic range ignores it, and the samples come back the same
either way — which is exactly why writing it wrong is worth being careful
about, since the round trip cannot tell you.

The field is nine signed bits of gain as a power of two in sixty-fourths —
`2^(g/64)`, a step of about 0.094 dB over a span of ±24 — three bits saying how
long the value stands, and four spare.

**It is a deadline, not a preference.** A decoder counts access units since the
last word and complains when more than `2^refresh` of them have gone by. It
counts the unit it reads the next word in *before* it reads it, so the gap
between two words may be `2^refresh` units and not one more. Testing the bound
before counting instead of after puts every word exactly one unit late — which
is what happened, and what one decoder said and the other did not.

**The start-up gain follows the gains.** The major sync carries what a decoder
joining mid-stream applies until an update reaches it, in sixteenths of a power
of two, and a decoder checks that it is no louder than the gain the stream is
already running at. So it is not a free choice: it is the smallest of the gains
in force, divided by the four that separates the two fields' units, rounded the
way that keeps the inequality true.

🔴 *Already running* means the word a decoder read last, not the one in the
unit it is reading. A restarting unit that raises a substream's gain, and said
a start-up gain that followed the new word, said one a step louder than a
decoder that never left was running; `harletty` warned `drc_start_up_gain too
large` on every such restart and went on; eight restarts of the two hundred and
eighty-three in a thirty-second slice did it. It follows the smaller of the two now — the word in force and the one
the unit states — which is under both.

What the reference does with it, over three thousand access units:

| | Units stating a gain | Range |
|---|---|---|
| 2-channel presentation | 23 | −7.6 … 0 dB |
| 6-, 8- and 16-element | 27 each | −3.6 … −1.3 dB |

About one unit in a hundred, and the two-channel presentation asks for markedly
more attenuation than the wider ones — which is what folding sixteen elements
into two costs in headroom.

**What gain to ask for is not this crate's decision.** `Encoder::set_dynamic_range`
writes what it is told and enforces only what the format enforces; the named
dynamic range characteristics are a phase 2 question and need a reference
encoder running under a licence its owner issued. `cargo xtask mlp --drc -4`
exercises the path end to end.

It costs two bytes per substream per statement and nothing else — measured
exactly, on every fixture.

## Extra data, and the Evolution frame in it

After the last substream an access unit may carry a block of extra data, and
what a decoder expects to find there is decided by **the major sync's flags,
not by anything in the block**: bit 12 set is an Evolution frame, clear is an
opaque payload handed on unexamined. The reference sets that bit and nothing
else, which is what its `0x1000` was.

A decoder enters the block whenever a whole 16-bit word is left in the unit, so
writing nothing is how a unit says it carries nothing — there is no empty
shape.

```text
┌────────┬──────────┬────────────┬──────────┬───────────┬─────────┬────────┐
│ check  │ length   │ reserved   │ frame    │ Evolution │ zeroes  │ parity │
│ nibble │ 12 bits  │ 4 bits     │ 12 bits  │ frame     │         │ 8 bits │
└────────┴──────────┴────────────┴──────────┴───────────┴─────────┴────────┘
└── not counted by ──┘└──────── `length` 16-bit words ────────────────────┘
```

Four things about it are worth stating, because each is a way to write a block
that parses and is wrong:

- **The length does not count the two bytes that state it**, and the frame's
  declared byte length is the room after the Evolution header rather than the
  frame's own size — a reader parses the frame structurally and pads to the
  end, so that field is a bound and not a measurement. Reproducing both from
  the frame's bit count gives the reference's own 38 words and 73 bytes, which
  is what says the rule is theirs rather than merely one that parses.
- **The check nibble is not a version or a type.** It is whatever makes the
  block's first two bytes fold to fifteen, and it is the only thing that
  distinguishes a block from padding.
- **A payload's own length is written in groups of eight bits**, and a second
  group is worth 256 more than it looks, because a continuation means the value
  so far was one short of the group's span. Sizes on both sides of that
  boundary are tested.
- **The frame closes with a protection field whose length is not free.** Two
  bits say how long the primary field is and two the secondary — none, eight,
  32 or 128 bits — and the code for none is *reserved* on the primary side.
  The reference always writes eight bits and no secondary field, and the byte
  changes every frame: a keyed digest whose computation the format calls
  implementation dependent, which no public decoder checks and which a
  decoder is told it may ignore. It is not a CRC of anything in the block —
  every eight-bit CRC, over every plausible range, was tried against 18 764
  reference frames and none matched. It is the leading byte of an
  HMAC-SHA-256 over the access unit and the frame with the field cleared —
  [`hz_mlp::protection`](../crates/hz-mlp/src/protection.rs) says exactly
  which bytes — under a key that is not this project's to ship. Given the
  key, from the local settings file, the encoder writes the digest and
  `cargo xtask thd` checks it: **18 764 of 18 764** fields on the three
  reference streams. Without one the field is written at the reference's
  length with a constant in it, rather than at the reserved length of zero.
  See [encode.md](encode.md#the-protection-field-and-the-key-that-fills-it).

The reference carries one payload, identifier eleven — object audio metadata —
of 65 bytes, in 53 access units out of 2000. Every field of its block was held
next to this reader's through the harness, and a block this encoder writes for
a sixteen-element programme is pinned in the tests.

**What is written today is the container and not its contents.** An encoder can
put an arbitrary payload in an access unit's extra data under any Evolution
identifier, and it comes back through both readers with every check verifying;
what has yet to be written is the object audio metadata that belongs in it.
`cargo xtask mlp --evolution` carries a stand-in of changing size to exercise
the path, and corrupting one byte of a block is reported as a bad block rather
than as a bad access unit — the audio beside it is still exact.

## A matrix that moves

Sync word C's second set of coefficients is a **step per access unit**: the
coefficient ramps across the unit and the whole step is added at the end of it,
so one statement tracks a trend for as long as the matrix stands rather than for
one unit. That is what makes it worth saying — and the measurement that decided
whether to write it was of the alternative.

**Restating the matrix every unit instead** was measured first, and it loses
everywhere: +17.8 % on correlated pairs, +1.7 % on a programme in stereo. What
is worth knowing is *why*, because the two costs point in opposite directions
— the description costs about half of it, and the other half is that switching
a matrix turns the signal a channel carries into a different signal, which the
prediction filter's carried history is then wrong about. On a scene whose
correlation stands still, per-unit matrices code **worse**: 8.3 bits a sample to
8.8.

So there is only something to track when the correlation actually moves, and no
fixture had one. A stream of pairs whose weight sweeps continuously does, and on
it per-unit matrices finally code better — 20.8 bits a sample to 20.6 — while
still costing 3.1 % more overall. A step captures that gain without the
description cost:

| | Without steps | With | |
|---|---|---|---|
| A sweeping correlation | 4 248 218 | 4 230 512 | **−0.42 %** |
| Correlated pairs, standing still | 1 913 480 | 1 913 480 | — |
| Correlated noise | 4 126 700 | 4 126 844 | +0.003 % |
| A programme in 7.1, doubled | 2 690 426 | 2 690 426 | — |

A threshold was tried, to skip steps too small to pay for themselves. It cost
184 bytes on the sweeping fixture to save six on the still one, and was removed.

**Only half the pairs can use it.** A matrix is declared by every substream that
can reach its destination, and those declarations have to agree — a decoder
stopping at the two-channel presentation must reconstruct the same audio a full
decode does. Only sync word C can state a step, so only a matrix whose
destination no earlier substream describes may move: in a sixteen-element stream
that is the second half of the channels.

**The ramp is not a division.** A decoder folds the drift down by eighteen bits
*before* scaling it by the sample index, and multiplies by an integer reciprocal
of the frame count rather than dividing. Writing the obvious arithmetic instead
gives a stream whose every checksum verifies and whose samples are wrong, which
is the third time that shape of mistake has come up here — so the round trip
runs at every point of the ramp and in every unit of an interval.

## What a shipped stream's matrices say

`harletty info --matrices` prints every matrix a stream declares, coefficients
scaled to real numbers, and `--stats` totals the block-level choices per
substream ([harletty PR #49](https://github.com/harletty/harletty-bridge/pull/49)).
Read against the thirty-second programme slice of [encode.md](encode.md), the
reference's four substreams do two different things with one syntax:

- **Substream 3, sync word C: eleven lifting steps.** Every row's coefficient
  on its own destination is exactly ±1.000 and the others are dense — up to
  eleven sources at fourteen fractional bits, dither scale 2 on nine of the
  rows. That is an integer lifting transform of the twelve elements: the
  internal channels are its output and a full decoder runs it backwards. Two
  rows, into channels 10 and 11 at ten fractional bits with a whole-matrix
  shift, change at every restart; the other nine read identically at every
  restart — a fixed structure with adaptive prediction on top.
- **Substreams 0, 1 and 2, sync words A and B: dense rows with no unit
  coefficient.** The two-channel presentation is a 2×2 mix of internal
  channels 0 and 1 (`0.796·ch0 − 0.713·ch1` and `0.500·ch0 + 0.713·ch1`); the
  5.1 presentation's six rows take up to five sources each, with destination
  coefficients like 1.819; the 7.1's eight rows likewise. These are not
  lossless steps and need not be: **the narrower presentations are computed
  at decode, by the matrices, from the internal channels**, and cost the
  stream nothing but their declarations — some forty bits a row, once per
  restart.
- **Constant across each restart interval.** 283 statements over 36 106 units
  in substreams 0–2, one per restart, 285 in substream 3, and interpolation in
  no block at all. A fold whose gains step every 2.7 seconds — which is what
  [fold.md](fold.md) measured from the outside as a property of the stream
  rather than of the moment.
- **The internal channel order is a permutation**, `[3, 1, 6, 9, 8, 0, 7, 2,
  10, 11, 4, 5]`: the first two internal channels carry what the stereo fold
  needs, the next four what 5.1 adds, and so on. The two objects, elements 8
  and 9, sit at internal channels 3 and 4 inside the 5.1 substream's range;
  two bed elements, 4 and 5, are rebuilt by the last substream from near-zero
  residuals.

Against that, this encoder's stream is a degenerate instance of the same
syntax: internal channels in master order, matrices it can now use for a
presentation but does not fill with a fold, and presentations that are
**copies of the leading elements** — decoded, its
presentations 0, 1 and 2 equal elements 0..1, 0..5 and 0..7 exactly, so a 7.1
decoder of it hears no objects. Writing the presentations the reference's way
costs no audio bits. Carrying two folded channels as audio instead, in the
slots of the silent elements, was measured at **+8 %** (14 668 390 bytes
against 13 605 276), which is the price of not doing it that way.

That paragraph describes the stream before the presentations were built, and
is still true of one written without `--presentations`. With it, the three
narrower substreams carry real folds of every element, stated as dense rows
the way the reference's are, and a 7.1 decoder hears every object — see
[Carrying the folds](#carrying-the-folds-for-six-per-cent-not-forty) below,
and what FFmpeg's matrix limit did to its cost.

The same tool on the same two streams, where the coding choices differ:

| | the reference | this encoder |
|---|---|---|
| second filter | order 1–2 in 65–88 % of blocks (substreams 0, 1) | order 1–2 in 40–79 %, since the fixed pair landed |
| first filter orders | 6–8 in 86–99 % of blocks | spread over 3–8 |
| channel parameters said | 30–60 % of channel-blocks | 7–57 % |
| codebooks | tables 1 and 2 (46 % / 47 %), table 3 in 2 % | table 3 in 34–43 % |
| output shift | 3, 4 or 5, per channel-block | 4 throughout |
| dither in the lifting rows | scale 2 | none |

The second-filter row read "never" when this table was first made; measuring
the reference's pair with the tool is what turned it around — see [the second
filter](#the-second-prediction-filter-which-pays-after-all). Whether that
pairing is why the reference's codebook use lands on tables 1 and 2 is still
open.

## What it does not do yet

**Clustering**: which objects merge into which of the fixed number of elements,
and how their positions and gains are interpolated over time. That is the

The payload that rides in the extra data — what the elements are, where they go

## Three things the format does not say plainly

**The major sync checksum has no endianness.** It is a CRC-16 over all but the
last two bytes, and those last two bytes are then XORed into it *byte for byte
in the opposite order* — the CRC's high byte against the first of them. FFmpeg
reaches the same place by holding its CRC register byte-swapped, XORing two
bytes read little-endian and writing the result little-endian: two reversals
and a swap that cancel. Ported as "little-endian", it produced a stream no
decoder would sync to. A real stream said so in one comparison.

**The substream checksum's initial value is 0x3c, not 0xa2.** FFmpeg writes
`0x3c` with a note that `crc_63[0xa2] == 0x3c`; the decoder crate in this
workspace states the same algorithm with an initial value of `0xa2`. Those look
like two ways of saying one thing. They are not: the register update is
`crc = table[crc ^ byte]`, so seeding with `0xa2` gives `table[0xa2 ^ first]`
where seeding with `0x3c` gives `table[0x3c ^ first]`, and they agree only when
the first byte is zero. Seeded with `0xa2` on exactly that reasoning, every
access unit was rejected by both decoders.

**The declared peak bitrate is load-bearing.** Every real stream declares
9.6 Mbit/s, so this one did too — and above 96 kHz the uncompressed coding
needs more than that. A decoder sizes its input buffer from the field: told the
stream peaks lower than it does, it reports the access units as arriving faster
than it can take them, which is what both decoders said. The encoder now
declares whichever is larger, the nominal figure or what its coding can
actually produce. The figure comes down on its own as the tools land.

## One gap that is shared, not ours

`truehdd` warns about "high-resolution output timing" every sixth access unit.
The bit FFmpeg calls `data_check_present` is, in that decoder's reading, one
bit of a timestamp serialised across successive units; writing a constant zero
makes the state machine reading it complain. **FFmpeg's own streams draw the
same warning**, which is how we know it is not something this encoder
introduced. The harness counts those separately and says so. A real encoder
presumably serialises something meaningful there, and working out what is
outstanding.

## The cost of saying anything, and why it was not taken

A channel whose filters, codebook and width are all what the decoder already
holds costs **one bit**: the bit that says it has nothing to say. One with
anything to say costs **eleven** before any description — that bit, a flag for
each filter, the offset flag, two bits of codebook and five of width. So a
candidate that changes nothing but its codebook costs ten bits more than one
that changes nothing at all, and the search did not know it: `best_entropy`
chose a codebook and a width without being told which pair was already in
force.

Two ways of telling it were measured. Both were byte-exact through the round
trip; neither is in the encoder.

**Ten bits on any candidate that has to say something.** This is the correct
differential: every candidate either costs one bit of framing or eleven, and
the difference belongs in the comparison.

| | whole fixture set | `prog_*` only |
|---|---|---|
| | −0.023 % | +0.039 % |

It does what it was expected to do, on the material it was expected to do it
on. On a sparse sixteen-element bed the share of channel-blocks that say
anything falls from 31 % to 27 %, a filter's life goes from 19.5 blocks to
40.6, and the stream is **0.42 %** smaller. On a programme in stereo the share
does not move at all — 55 % either way — because nearly every block of dense
material genuinely has something new to say, so the ten bits buy nothing and
only tilt the choice between describing a filter and keeping one. That tilt is
the loss: the stream grows 0.14 %.

**Ten bits only where the filter is not being restated**, which is the narrower
rule that leaves the filter/no-filter balance — and so the quarter share the
amortisation is calibrated at — alone. It is much worse: **+0.378 %** over the
set, +1.2 % on a sparse bed, +1.6 % on a real eight-channel mix, +2.3 % on a
tone. Making the coding sticky without making the filter sticky churns the
residuals instead.

So the rule stands: a lever that wins on synthetic fixtures and loses on
`prog_*` is not taken. What this measurement leaves behind is the number — ten
bits — and the knowledge that the gain is real on sparse material and is
cancelled by the interaction with the filter share. A rate model that decided
the filter and the coding *together*, over a whole interval rather than a
block, would not have that interaction to lose to; that is the two-pass
decision, and it is where this belongs.

## Offering a first filter without the second, and why it churns

When a second filter is in force, every candidate the block sees is a pair
built on it: the first filter is fitted to what the second leaves, and a plain
first filter is not offered at all. That looked like an omission — the block
can express a pure first filter, and sometimes a pure one is better — so it was
offered.

It is worse everywhere that matters, by a lot:

| fixture | full | fast |
|---|---|---|
| prog_mono | +0.768 % | +0.818 % |
| prog_stereo | +0.739 % | +0.958 % |
| prog_51 | +0.713 % | +0.863 % |
| prog_71 | +0.815 % | +0.805 % |
| prog16 | +0.673 % | +1.048 % |
| busy16 | +1.061 % | +0.933 % |
| bed16 | +0.785 % | +0.796 % |

Whole set +0.567 %, the programmes +0.808 %. What it wins is a few hundredths
of a per cent on noise and tones, where a second filter was never paying
anyway.

The reason is churn, and it is the same shape as everything else the block
search gets wrong on its own: a block that takes the plain filter *drops* the
second one, and the next block that wants it has to state it again along with
the history it starts from — a description the block that dropped it never saw
in its own comparison. The search is greedy over forty samples and the second
filter lives for an interval, so a candidate that is cheaper for this block and
dearer for the twenty after it wins the comparison it is offered.

Not taken. It is also the one place where a lever's cost and its speed point
the same way: not offering the pair is worth 7 to 16 % of the encoding time.

## What the reference does with its matrices, which is not what we do

`harletty info --matrices` over a reference stream says something the encoder's
use of the field does not prepare you for. Counted over one programme, 288
restart intervals:

| substream | matrices | distinct configurations over the programme |
|---|---|---|
| 0 — two channels | 2 | **1** |
| 1 — six channels | 6 | **1** |
| 2 — eight channels | 8 | **1** |
| 3 — the elements | 11 | rows #0 and #1: **286**; rows #2–#10: 6 to 20 |

The first three substreams' matrices **never change**. They are not fits and
they are not decorrelation: they are the authored fold, written as lifting
rows, and they are what makes a decoder stopping at the six-channel
presentation hand back a 5.1 mix of the elements rather than the elements
themselves. The presentations are *computed by the matrices*.

In the last substream the labour is split. Two rows — the ones writing the top
two channels, at ten fractional bits rather than fourteen — are refitted at
almost every restart: those are the compression. The other nine change six to
twenty times over the whole of it, which is what a fold that follows the
programme rather than the signal looks like.

### What this encoder can now state, and what still stops it

`Encoder::set_presentation` states a presentation on any substream but the
last: rows that compute what a decoder stopping there hands back, written with
`Primitive::dense` or `Primitive::rounded` — the first constructors here whose
destination coefficient is not one, because a presentation's rows have no unit
coefficient anywhere in them. `declared_by` routes them, and the matrix
parameters are now written on a restart even when nothing is rematrixed for
compression, which they were not before.

Measured, on a six-channel stream with content on every channel:

| | presentation 0 | full decode |
|---|---|---|
| without | −16.9 / −16.9 dBFS | — |
| with a 2×2 row pair | −16.4 / −22.4 dBFS | **byte for byte the same** |

Both halves matter. The presentation changed, so the rows reach the substream
that computes it; the full decode did not, so they never reach the substream a
full decode reads — which is the invariant that makes a non-invertible row safe
to write at all. `cargo xtask mlp --presentation` is that check, and ffmpeg
reports the round trip bit exact with the rows in.

🔴 **What that does not buy is the fold**, and the reason is worth stating
because it is not the one this section assumed. A decoder stopping after
substream 0 has decoded **that substream's channels and no others**, so the
rows it applies can only read those. Substream 0 of an object programme carries
channels 0 and 1: its presentation is a 2×2 mix of two elements, and no
declaration can make it a fold of all twelve, because the other ten are not
there to read.

That is what the reference's permuted internal channel order is for — `[3, 1,
6, 9, 8, 0, 7, 2, 10, 11, 4, 5]`, whose **first two internal channels carry
what the stereo fold needs**. Writing real presentations is therefore not a
matter of declaring a fold: it is arranging the elements so each presentation's
leading channels already carry theirs, with the last substream's rows rebuilding
the elements from all of them. The declaration is the cheap half, and it is the
half that is now written.

### Arranging the elements: the transform, built and proved exact

[`hz_mlp::arrange`](../crates/hz-mlp/src/arrange.rs) is that arrangement. It
takes the fold rows and how many leading channels each may live in, and returns
the cascade of lifting steps that puts each fold into one of them, with the
channel it landed in and the scale the presentation's own matrix has to divide
out.

**Why it cannot cost a bit.** A step reads every channel but its destination, so
the sum it adds is the same quantity before and after it runs. An encoder that
subtracts *that same shifted sum* undoes it exactly — whatever the coefficients
are, whatever the shift truncated.

🔴 That is not the same as negating the coefficients, and the first version did
negate them. A shift is a floor, so `(−x) >> 14` is `−⌈x/2¹⁴⌉` rather than
`−⌊x/2¹⁴⌋`: a cascade built that way loses a sample wherever the sum is not a
multiple of the shift, which is nearly everywhere. The test caught it on the
first run. The two directions share one set of coefficients and differ only in
the sign of what they add.

**How a step is chosen.** Write `U` for what the channels currently hold as
combinations of the elements. Expand the fold row in it, `f = Σ g_i·U_i`, give
the step to the channel `h` with the largest `|g_h|` among those the
presentation carries, and declare `−g_i/g_h`. The destination's own coefficient
works out to one — which is what a lifting step is — and the channel ends up
holding `f/g_h`.

**And why the element order decides whether it works at all.** The coefficients
are divided by the host's own, and the field holds a little under two, so the
host has to be a big contributor — but it also has to be *inside* the
presentation. Those pull against each other, and what settles it is which
element is stored in which channel. Measured in the tests: the same fold and the
same two channels cannot be written with the elements as they come, and can be
once they are ordered.

### What a twelve-element scene said, and what it cost to believe

Trying it on a real scene — twelve elements, a ring at ear height and four
overhead, folded to 2.0, 5.1 and 7.1 by `ObjectFold` — took four attempts, and
three of them were wrong for reasons worth keeping:

- **One step per row is not enough.** That scene's stereo rows have a host
  contributing 0.349 against a biggest of 0.729: a ratio of 2.09 against a field
  that holds two. It misses by four per cent. The answer is to write the same
  step *clamped* and repeat it — each pass takes `REACH · g_host` off the worst
  coefficient — which costs a step and always converges.
- **Greedy element order is not enough, and neither is most-constrained-first.**
  The 5.1's surround rows and the 7.1's back rows want the same elements; served
  in either order, whichever goes first leaves the other with nothing, though it
  had six other elements it could have taken. It is an assignment problem and it
  is solved as one, by augmenting paths.
- **The host cannot be chosen row by row and kept.** A channel's share of a row
  is its coordinate in the basis the channels *currently* hold, and every row
  hosted changes that basis. With the 5.1's surrounds hosted, the 7.1's back
  rows have a coordinate of **exactly zero** on the two channels left to them —
  though those channels hold the very elements they are made of. So the
  assignment is searched, with backtracking, over at most sixteen rows once per
  stream.
- 🔴 **And a row does not need a channel at all.** What a presentation needs is
  that its fold lie in the **span** of the channels it carries, because its own
  matrix set can then produce it; hosting is only how a row that does not yet
  lie there is brought in. Demanding a host per row fails on rows that are
  already reachable, which on a real scene is most of them.

Ordering the elements is worth 3 rows of 7 to 6 of 7, measured on that scene.

### 🔴 The last row, and what it meant

Six of seven, ordered or not. The two rows the 7.1 adds reach the **height**
elements, stored in channels 8 to 11 — outside the eight the 7.1 carries. They
have to be brought into a channel below eight, and by then the 5.1's rows hold
all but one of those: one of the two gets it, the other has nowhere to go.

That is not a better permutation waiting to be found. It says the element order
is not the last degree of freedom left, and that **the stored channels are not
elements in a clever order at all**.

## The hierarchy of presentations

[`hz_mlp::hierarchy`](../crates/hz-mlp/src/hierarchy.rs) is what they are
instead. For presentation `k` carrying `n` channels, what has to be true is

```text
span{ stored[0], …, stored[n-1] }  ⊇  span{ presentation k's rows }
```

— a superset is fine and a subset is fatal. The prefix has to *reach* every row,
since the presentation's matrix can only combine what it reads.

So it is built narrowest first, each row reduced against the rows already
chosen. A row that adds a dimension is stored as it stands, so channel 2 carries
the centre rather than some rotation of it; a row already in the span is skipped,
having nothing to carry. Two things fall out rather than being handled: a
presentation can need **fewer** channels than it carries — the low frequency
channel of a 5.1 takes nothing from an object, so on a programme with no low
frequency bed it adds no dimension and the channel is filled with an element —
and the rows the last presentation wants come free, since whatever is left over
is completed with elements, which is "what restores the elements" stated as a
basis rather than as an intention.

On the twelve-element scene it gives

```text
within  [2, 2, 6, 6, 6, 6, 8, 8, 12, 12, 12, 12]
```

which is the shape a shipped stream has: the stereo pays for two channels, the
5.1 for four more, the 7.1 for two, and four restore the elements.

### And a row may only be hosted in the channels its own presentation adds

The rule that made the cascade correct, and it was not obvious. Hosting a row
anywhere inside its reach looks harmless: a 7.1 row may read channels 0 to 7, so
why not host it in channel 4? Because channel 4 is inside the 5.1's prefix, and
the 5.1's own rows were left alone precisely *because* they were already in that
prefix. Rewriting the channel takes them out of it.

Measured before the rule went in: the stereo carried its fold to 1.6e-5 and the
5.1 missed its own by **1.8**. After it, every presentation reaches its own rows:

```text
presentation 0 (2 ch)   8.1e-5
presentation 1 (6 ch)   1.0e-4
presentation 2 (8 ch)   3.1e-4
presentation 3 (12 ch)  0
```

Which is not zero and is not meant to be. The coefficients are fourteen-bit, so
a channel carries its row to about `2⁻¹⁴` and a cascade accumulates a few of
those; a fold is carried to the precision of the field it is written with.
What is exact is the programme, and the round trip is what says so — asserted on
this very cascade, twelve channels of awkward samples through `unapply` and back
through `apply`.

`the_hierarchy_carries_what_an_element_order_cannot` in `hz-cli` holds both
halves, because the second only means anything against the first.

## Wired into the encoder, behind `--presentations`

`Encoder::set_arrangement` takes the cascade, the rows each substream declares
and the channel assignment that goes with them, **together**: the declared
matrices stand for a whole restart interval, so an arrangement adopted in the
middle of one would code samples the header does not describe, and presentations
written over what a *different* arrangement left are presentations of nothing.
One field, one adoption point, at the restart where the coding matrices are
decided.

The encoder undoes the cascade before it codes anything and the last substream
declares it after its own coding matrices, so a full decode runs the whole thing
backwards. Verified against `truehdd` on a real master: the elements come back
**byte for byte identical** to a stream written without an arrangement.

Four things had to be got right, and each was wrong first:

- 🔴 **The coding matrices come first.** A decoder stopping early applies *only*
  what that substream declares, and the channels it has are still in the domain
  the coding matrices put them in. A presentation stated on its own is stated
  over the wrong signal.
- 🔴 **The rows are applied one after another, not all at once** — each one
  *assigns* its destination, so a row written after another reads that one's
  *result*. Which is not a hazard to work around but the mechanism: the
  reference's 5.1 is **six matrices for six channels**, destinations 5, 1, 0, 3,
  2, 4, each reading whatever the ones before it left. Factoring into two
  triangles instead costs twice the matrices and a permutation on top — 23 rows
  against the 15 a substream may declare.

  So it is one row per channel, in an order chosen as it goes: a channel may
  only take a row it holds a real part of, and the channel of the *same number*
  is preferred. The cost of a row says nothing about what it leaves for the ones
  after it, and reading it greedily takes a cheap cross pairing now for an
  impossible one later — measured as a 5.1's left computed in channel 1 because
  that channel's dead bits made it look cheap, leaving its right to be computed
  in channel 0 at a coefficient of ten.

  Which is why [`hierarchy::build`] stores each presentation's channel `j` in
  channel `j`: the diagonal has to be there to be taken. Storing whichever row
  adds a dimension next puts the 5.1's *left* in the first channel it adds,
  though its left comes out where the stereo's does.

- 🔴 **The matrix permutes, and the permutation goes in the channel
  assignment.** A 5.1's left is built where the stored row it is made of sits,
  not where the 5.1 wants it. Saying that in matrices costs three of them per
  transposition — **23 rows for a 5.1, against the 15 a substream may declare**
  — and the format has a field for it. With it: 3 rows for the 2.0, 8 for the
  5.1, 11 for the 7.1. That the field means what it looks like was measured, not
  assumed: swapping it swaps the decoder's output channels exactly.
- 🔴 **The dead bits are per channel, and a row that mixes channels has to
  carry the ratio.** A decoder shifts each channel back up *after* the matrices
  and by that channel's own amount, so a channel shifted down by three and one
  shifted down by four are not in the same units. Ignoring it came out as a 5.1
  whose low frequency channel was nine decibels loud and whose left surround was
  fourteen quiet.

  Which is what the reference's rows carry too — its stereo substream states
  `[3, 4]` for its two channels — and where its amplifying matrices get their
  headroom. Written over the elements, presentation `j`'s row wants
  `2^(s_e − s_c)` of element `e`, where `c` is the internal channel the
  factorisation ends up computing it in. The sources' half goes in before the
  hierarchy is built; the destination's half is **split across both triangles**
  — `D·U` going down and `D·L·D⁻¹` coming back up — because putting all of it in
  the last row leaves the first one carrying the sources' shifts alone, which
  measured as an upper triangle asking for eight times what the field can say on
  shifts that were all the same.

### What it produces, measured

A twelve-element programme, against the master's own 7.1-then-fold 5.1:

```text
  L    fold -47.23 dB   stream -44.98 dB   correlation 0.846
  R    fold -49.68 dB   stream -46.63 dB   correlation 0.808
  C    fold -59.70 dB   stream -57.70 dB   correlation 0.842
  LFE  fold -68.29 dB   stream -68.28 dB   correlation 1.00000
  Ls   fold -51.93 dB   stream -50.97 dB   correlation 0.801
  Rs   fold -54.62 dB   stream -52.84 dB   correlation 0.762
```

The low frequency channel is **exact**, which is what says the chain is right:
it is a pass-through with a known answer, and it comes back to a hundredth of a
decibel and unity correlation. The rest is the fold's own approximation — the
presentation matrix stands for a whole restart interval while the objects move
through it, so it is the fold of where they were when it was written. Restating
it more often, or ramping it, is the next thing to try.

### 🔴 And why it is off by default

A cascade **stores more than it was given**: a host ends up holding its row
divided by its own share. The codec's domain is twenty-four bits and a decoder
enforces it by refusing the stream outright — "positive saturation from huffman
decode". The dead bits are the headroom, so the encoder settles the interval's
shifts first and then *runs* the cascade over the interval's own samples to see
whether what it stores fits. Bounding it instead means bounding a sum of
magnitudes, which assumes every element peaks at once and in step: measured at
3.16x full scale on a programme whose cascade fits with room to spare.

A programme with no room is written without folds. `crowd40`, whose mix clips at
+1.2 dBFS, is one.

### 🔴 And the coding matrices after it, which were not checked

The cascade was run against the domain and kept only where it fit. The coding
matrices decided *after* it were not: a matrix's weight is a least-squares fit
over the interval, which takes energy off on average and not on every sample,
and it is costed on four units of the hundred and twenty-eight it stands for.
On a unit where the sources swing the other way it adds — and a leading
channel holding a fold amplified by its host's share has no room for that.

Measured on a re-voiced programme, twelve elements copied from the original
and five sources panned onto them, with the folds on: **fifty-four samples
past the domain in the first two substreams**, none in the elements
themselves, none with the folds off, and none in the same programme folded by
the clusterer — whose limiter had left every element with room the copied
ones did not have. The reference decoder reports each as a saturated
recorrelator and refuses the stream; the elements decoded fine, so nothing
listening to the full presentation would have said so.

So the same bound is now on the matrices, twice: a candidate that would leave
the domain is refused where it is judged, so that another can win, and a
decided matrix is dropped on what is really stored, steps and all, with the
interval matrixed again from what is left. `a_matrix_that_would_leave_the_domain_is_refused`
pins it, against a test decoder that holds the reference's bound — which it
did not before, and which is why the round trips had never seen this.

The bound is the syntax's, not one number: twenty-four bits under restart
sync words A and B, and the whole thirty-two-bit word under C, whose filters
run that wide — which is how the reference decoder holds them, and why a
channel of the immersive substream stores past twenty-four bits and decodes.

What it costs, on the first thirty-one minutes of that programme: three
candidates refused where they were judged, seven decided matrices dropped on
what was stored, and a stream **two kilobytes smaller** than the one that did
not decode. The seven are why the second bound is not the first said twice:
it judges a candidate on the weights it starts with, before a step has moved
them and before the matrices beside it have been kept or dropped, and a drop
changes what every matrix reading that channel stores. `HZ_DOMAIN=1` in the
environment says each refusal and each drop as it happens.

### 🔴 Eight matrices, not fifteen

The count is a four-bit field and sync words A and B write it as itself, so
the encoder allowed fifteen — and with the folds on wrote up to fourteen in
the 5.1 and 7.1 substreams: the presentation's rows, and the coding matrices
on top of them. FFmpeg's decoder, which is the decoder inside every player
that is not Dolby's, stops at eight (`MAX_MATRICES_TRUEHD`), and the reference
streams write exactly the rows: **two, six, eight**, and nine in the immersive
substream FFmpeg never reads.

Written past eight, a re-voiced programme was refused by FFmpeg unit after
unit, and the refusal cascaded into "IIR filter order 9", "quant_step_size
larger than huff_lsbs", "substream 2 length mismatch" and "restart header
sync incorrect" — none of which was wrong in the stream, all of which a
decoder thrown off its place reports. The reference decoder reads all of it
without a word, which is how the stream shipped that way: the scanner that
found it only remuxes, and the player this encoder is written for decodes
with that reference.

So the bound is eight for A and B, rows and coding matrices together, and
sixteen stays for C. Measured on a minute of that programme: the same ten
intervals go without folds as before — the rows, not the bound, decide that
— and the stream is 1.6 % larger for the coding matrices the 5.1 and 7.1
substreams no longer carry. FFmpeg then decodes it without a complaint.
`no_early_substream_declares_more_matrices_than_every_decoder_reads` pins it,
on elements alike enough that every one of them would have taken a matrix.

### 🔴 What carrying them costs, and where it goes

Measured on the same programme, two thousand access units, against its
reference stream:

```text
  reference       355.3 B/unit    (sixteen channels, and it carries folds)
  ours, no folds  331.1 B/unit    0.93x the reference
  ours, folds     462.7 B/unit    1.30x the reference, 1.40x ours
```

So the reference carries its folds for about seven per cent over what our
fold-free coding costs, and ours cost forty.

**Where it goes is not a mystery.** The energy of each channel, before the
cascade and after, in dBFS:

```text
  before  −89  −140  −318   −89   −81   −85   −91   −84   −72  −318  −143   −74
  after   −51   −73   −79   −78  −105   −85   −94   −83   −70  −318  −143   −74
```

Three channels that were quiet or **silent** now carry the folds. The elements
are sparse in energy — objects come and go, and several are nothing at all —
and a fold is never nothing. Channel 0 goes up by 38 dB, which is six bits a
sample on that channel alone, and channels 1 and 2 by more.

Three things it is **not**, each measured and each a plausible guess:

- Not the matrix budget. The last substream declares fifteen matrices against a
  ceiling of sixteen, which looks like it leaves the coder nothing — but without
  folds this encoder declares **zero** coding matrices anyway, so there was
  nothing to crowd out.
- Not amplification. The cascade's worst is 1.01x: a host ends up holding its
  row divided by its own share, and the shares here are all near one.
- Not the element order. Ordering them so the loud ones lead moves the one
  channel that holds eight times its inputs from channel 0 to channel 2; it does
  not remove it, because what makes a fold channel loud is that it is a sum of
  everything rather than which element it is hosted on.

### 🔴 Which basis to store, measured four ways

Any basis of a presentation's added dimensions carries it, so which one to store
is free — and it is where the forty per cent is. Four of them, costed on a real
interval as the sum over channels of `log2` of what each would actually hold
(its own variance under the elements' measured covariance), beside how many
lifting steps the cascade needs to reach it:

```text
  the elements themselves          77.4 bits    (no folds at all)
  the innovation basis             93.1 bits    34 steps
  reduced eight tenths of the way  95.3 bits    32 steps
  reduced three tenths             100.5 bits   29 steps
  the presentations' own rows     103.8 bits    15 steps   ← what is stored
  the elements, loudest leading    113.6 bits   12 steps
```

So the lever is real: storing the **innovation** — each row with what the
earlier channels already explain taken out of it — is worth 10.7 bits of the
26.4 the folds cost, about forty per cent of the gap.

🔴 **And it does not fit.** A substream may declare sixteen matrices. The rows
as they stand take fifteen; reducing them by *any* amount at all takes
twenty-nine, and the full innovation thirty-four. The reason is the same one
that makes the reduction worth something: a reduced row is a difference, which
is quiet but poorly aligned with any one channel — and a lifting step keeps its
destination's coefficient at one, so a row whose share on its host is small has
to be brought in by repeated steps clamped to what the field can say.

Which is worth stating as a rule, because it is what closes off the obvious
ideas: **a lifting cascade stores a row divided by that row's share of its host,
so what it costs to store is the inverse of how well the row lines up with a
single channel.** Quiet rows are exactly the ones that line up badly. The two
pull against each other and sixteen matrices is where the argument ends.

Note also what the fourth line says: ordering the elements so the loud ones lead
gets the step count down to twelve — nearer the reference's eleven — and costs
ten bits more. Steps and bits pull against each other too, and the count is not
the thing to minimise.

### 🔴 And the reference does the same thing, which was misread once

This said, for a day, that the reference does *not* use lifting steps — that four
of the eleven matrices its last substream declares scale or discard their
destination, and that this was what let it store folds at natural amplitude. It
was wrong, and it was wrong because the reader had the presence mask backwards:
the immersive syntax names its sources from the **least** significant bit up
(`frame::mask` is what writes it), and reading it the other way round puts every
coefficient on the wrong channel.

The giveaway was there to be had and was not taken: this encoder's own streams
are built from nothing but lifting steps, so reading one back must show a
destination coefficient of one every time. It showed zero. **A reader of a format
this project also writes can always be checked against what it writes.**

Read correctly, the reference's last substream is:

```text
  dest 10   own −1.000   dest  1   own +1.000   dest  4   own +1.000
  dest 11   own −0.500   dest 10   own +1.000   dest  0   own +1.000
  dest  6   own +1.000   dest  7   own +1.000   dest 11   own +0.500
  dest  3   own +1.000   dest  2   own +1.000
```

Nine of the eleven are ordinary lifting steps — a destination of −1 among them,
which is exactly invertible too. The two that are not are both on channel 11 and
both carry the syntax's per-matrix shift, which this encoder never writes, so
what they mean is not something to be guessed at from here.

So the reference's lossless cascade is built the same way ours is, and the
difference in what it costs is not in the kind of step. What it does do is get
there in **eleven** steps where ours takes fifteen, with coefficients that stay
near one. Which puts the question back on the arrangement itself — how many
steps it takes and how well conditioned it leaves the channels — rather than on
the format offering it something we are not using.

Three things the reference's rows use and `hz-mlp` still cannot write:

- **The channel assignment is a permutation.** `[0, 1, 5, 4, 2, 3]` for the
  six-channel presentation, `[3, 1, 6, 9, 8, 0, 7, 2, 10, 11, 4, 5]` for the
  elements. This encoder writes the identity. The permutation is how a fold
  can put its output where the presentation's channel order wants it without a
  further matrix.
- **`frac_bits` is chosen per matrix**: 0, 6, 10, 13 and 14 all appear. Zero is
  a row that only copies a channel. Ten is what the two refitted rows use — a
  coefficient four bits cheaper, twelve of them per row.
- **Dither is stated**: 2 on the last substream's rows here, 5 on another
  programme's. This encoder writes none.

None of that is a defect in what the encoder does today. Decorrelating a
channel against its neighbours and computing a presentation are two uses of the
same field, and the first is what a lossless coder wants. But a transcoder that
must reproduce the reference's *presentations* — which is what
[`fold.md`](fold.md) measures and what phase 2 needs — has to write the second,
and that means the sign, the permutation, the per-matrix precision and the
dither. Not in this branch.

## Carrying the folds for six per cent, not forty

The forty per cent above was three defects and one thing never tried, and
each was measured on its own before anything was changed.

### Where it went, by substream

The twelve-element programme above, the first two thousand units, bytes per
unit in each substream — and its reference stream, which carries its folds:

```text
                 no folds     folds     reference
```

### Three things that were wrong, measured

- **The amplification was real, and misreported.** The stream carried five
  clamped steps into channel 0, and the transform they compose has a
  coefficient of 8: channel 0 held a stereo row at eight times its size, three
  bits a sample on the densest channel there is. `amplification()` said 1.01x
  because `write_row` returned the host's share at the *last* of those steps,
  which is near one whatever the first one divided by.
- **Element 0 is the low frequency bed, and it sat in the stereo pair's
  channels.** It carries nothing of the stereo fold, so the row hosted there
  had no candidate, and the helper step manufactured a host with a share of
  an eighth. The reference keeps its bed at internal channel 5, inside the 5.1.
  The same defect is what made the twenty-four bit domain overflow on a
  programme mixed near full scale.
- **No coding matrix was ever chosen while folds were carried**, and the
  argument that none was needed — "without folds the encoder declares zero
  anyway" — was about different channels. The stored channels are dense sums
  and correlated; the covariance of the elements says the hierarchy as stored
  costs **112 bits** a sample over the twelve, the elements 83, and the same
  hierarchy with each channel predicted from the ones before it **77**: less
  than the elements. Folds are free, in that model, for any basis — a lifting
  cascade has determinant one, so the sum of the channels' log-amplitudes is
  bounded below by half the log-determinant of the covariance whatever the
  basis, and prediction from lower channels reaches it without touching any
  presentation's span. Three things stopped the encoder finding any of it: the
  cascade took fifteen of the last substream's sixteen matrices; the candidates
  were suggested on the *elements* and then costed on the hierarchy, so every
  weight described a signal the channel no longer carried; and a candidate was
  judged on its first unit alone, where forty samples of a three-bit gain never
  paid a two-hundred-bit description that stood for a hundred and twenty-eight
  of them.

### What changed

- **One step per row**, through the shift the immersive syntax puts on a whole
  matrix — `Primitive::wide` picks the smallest that holds the coefficients,
  which reach `2^(shift+1)`. Fifteen steps became four; the amplification is
  measured from what the channels hold.
- **The elements are permuted into the internal channels**, the last
  substream's channel assignment putting them back in order, and the
  permutation is a maximum-weight matching (`arrange::place_elements`): a row
  on an element weighs `log2(share) + log2(loudness)`, a channel no row takes
  weighs nothing, and the Hungarian method decides hosts and fill together.
  The weight is not "biggest share": a loud element at a third beats a quiet
  one at unity by several bits a sample, because the quiet one then sits raw
  in the last substream. 🔴 And a fill slot must weigh nothing: rewarded for a
  loud element, it counted that loudness twice and sent the loud elements to
  the slots — on the second half of the programme the 5.1's surrounds were
  hosted on two elements of four and a half bits, storing the fold at twelve,
  while the two loud ones they were folded with sat raw at ten. The
  hierarchy's widest presentation is filled in the matching's order rather
  than by element number, which is what lets the silent elements be the ones
  stored as they are.
- **The coding matrices are suggested on the channels as they are stored**
  — permuted, dead bits off, cascade taken off — and each candidate is judged
  on four units spread over the interval with its description charged once.
  Every substream's four-bit count is now a budget the search respects. The
  fold-free stream gained from the same judgement: 662 300 to 653 684 bytes.
- **An early substream certifies what it puts out.** With a presentation
  stated that is the fold, so its lossless check is computed by running its
  rows over the channels the way the decoder does, then shifting each by what
  the substream states. The elements' check had been written there before,
  which the reference decoder warned about at every restart and went on; the
  decoder in `tests/decoder` refuses it. The same substream declares the whole
  domain as its output width, since a fold can be wider than any element.
- The reference decoder in `tests/decoder` reads the channel assignment the way
  the real ones do — `field[matrix channel] = output` — which no earlier stream
  could tell, every presentation's permutation having been its own inverse.
  A twelve-element round trip through a hierarchy of presentations, with a
  six-cycle in its assignment, is now a test.

### The stereo pair, and why it is not a target on its own

The pair was 18 % over the reference's on the whole slice, the largest gap of
any substream, so it was taken apart. What the reference's two channels are,
read off its own cascade, is a **mid and a side of the stereo fold at four
tenths and seven tenths of their size** — its 2×2 presentation
(`0.796, −0.713 / 0.500, 0.713`) is exactly what undoes that — where ours are
the fold's two rows at twice theirs, each hosted on the element that carries
half of it. The scale alone is `log2(4 / 0.28)`, 3.8 bits a sample on the
pair, nineteen bytes a unit: the whole of the gap.

And it is not a saving. A lifting cascade is a bijection on the integers, so
the sum of what its channels cost can only fall by what cross-channel
prediction takes out; a scale moves bits from one channel to another and the
low bits it takes off a channel arrive somewhere. Where the reference's arrive
is its last substream, which costs 2.41 MB against our 1.63 — more than the
0.63 MB its stereo pair is under ours. The right comparison is the whole
stream, and there the pair's scale is nothing. What the pair *can* gain is its
own mid/side matrix, and it does, once a description is charged in proportion
to the units it is judged on.

Four things were measured on the way, and three put down:

- **A presentation is written at whichever of its shifts takes the fewest

- **`FIT_CONTEXT` 512**, measured over the fixture set: 0.26 to 0.40 %

- Put down: eight matrix sources again, now with the description charged in

### What FFmpeg's matrix limit cost

The 5.8 % above was measured with coding matrices free to go into any
substream. FFmpeg's decoder, the one in every player that is not Dolby's,
reads at most eight matrices a substream under restart sync words A and B —
see [`matrix::MAX_MATRICES`](../crates/hz-mlp/src/matrix.rs) — and the 7.1's
eight presentation rows already take all eight. So no coding matrix fits into
channels 0 to 7 any more; only channels 8 to 11, in the last substream, still
get them. Written past the limit, the stream was refused unit by unit by
every such player while `harletty` and the test tree's decoder read it fine.

On the slice, measured on 22 September 2026:

| | bytes | × reference |
|---|---|---|
| plain master, no folds | 13 282 388 | 0.988 |
| plain master, folds | 14 811 256 | 1.102 |
| `--cluster 12`, no folds | 13 078 364 | 0.973 |
| `--cluster 12`, folds | 14 586 432 | 1.085 |
| the same, before the limit | 13 893 014 | 1.033 |

**Carrying the folds costs 11.5 % over the fold-free stream today**, not
5.8 %, and the limit alone is 5.0 points of it. On a thirty-one-minute overlay
encode the limit cost less, 2.8 % (1 449 250 184 → 1 489 895 714 bytes), and
that is the figure to hold a feature-length encode to.

The reference pays nothing for the same constraint. Its stored channels are
already decorrelated, and the correction is folded into the presentation rows
it declares anyway, which it would declare regardless; its 7.1 substream
carries eight rows and no coding matrix. `cargo xtask ffmpeg-check` holds
every stream the harness writes to the limit, and the test tree's decoder
reads no more than FFmpeg does.

### Decorrelating the hierarchy, one channel at a time

The same idea, done here: each early channel has what the channels below it
predict of it taken out, by a lifting step in the last substream's cascade —
which has room — and the early substreams' rows are rewritten over what the
channels then hold, at no extra rows. See `Encoder::decorrelate`.

What it can be worth was measured first, with the steps forced in and the old
rows left standing — narrow presentations that decode wrongly, and a size that
is the coding gain alone:

| | slice, `--cluster 12` | 31 min of an overlay |
|---|---|---|
| every step forced in | −5.5 % | −3.7 % |
| a step kept only where the rows can still be written | **−1.56 %** | **−1.44 %** |
| all the steps of an interval or none | −0.49 % | — |

What stops the rest is not the order of the rows, which `rows_over` already
chooses, but their size. The saving is the elements two channels share, and a
channel with them taken out holds a small remainder: rebuilding a presentation
from it takes coefficients of 30 to 130, where the field stops under two —
mostly in the 5.1, and the 7.1 has no spare row to scale one up with. So each
step is kept only if every presentation can still be written after it.

Put down on the way: decorrelating only within a substream (+0.88 %, worse
than nothing), and keeping the prediction orthogonal over the elements to what
the channel holds, so that it keeps its size (no gain at all — the two cannot
be had apart). The threshold a step has to clear is modelled from the raw
energy, which predicts the coded cost badly; one step at a time, 500 bits and
2 000 come to within 0.04 % of each other.

Validated on the slice and on five minutes of an overlay: the elements byte
for byte, every narrow presentation matching the one written without it to a
correlation of 1.000000 and within 0.0004 dB, FFmpeg silent. With it, the
slice folded with `--cluster 12` is 14 358 334 bytes: 1.068 of the reference,
and folds cost 9.8 % over the fold-free stream. The rest, up to the 3.7 %,
needs rows that can reach a small channel — a presentation's shifts per
channel, which the reference states, are the next thing to try.

## The search that ran for minutes, and the reservation that ends it

Encoding a programme with `--presentations` from the application it is meant
for ran at a core and a half of thirty-two and produced a fifth of a minute of
audio a minute: five times slower than real time, one thread at a hundred per
cent and the pool asleep. It reproduced three and a half minutes into the
programme, and the log said what it was — the arrangement's search backing out
of row 5, fourteen million times a minute, on one interval.

The search hosts the hierarchy's rows one after another and backtracks when
a later one cannot be placed. What could not be placed was nothing: the block
of six closed with its centre row leaking **all** of itself. The centre was a
row the channels already held — the element it is made of, sitting in the
channel the matching put it in — so it needed no step and took no channel.
And a channel not taken is the next row's best host: the surround row took
it, the centre was gone, the check at the close of the block said so, and
the search backed out through every host and every helper step the block had
before giving up. Then it gave up, the interval was written without folds,
and the next interval did the same.

Two things, one of them the fix and one of them the guard:

- **A row that needs no step reserves the channels of its block that carry
  it** — whichever its expansion has a real part on. Four minutes of that
  programme: 2 250 intervals arranged, 0 refused, 95 back-outs where there had
  been 2.3 million, 21.8 s against 17.7 s without presentations, 750 % of the
  machine against 894 %. The slice measured above is unchanged to the byte.
- **The search has a budget**, `SEARCH_BUDGET` = 1 024 attempts, after which
  it says no and the interval is written without folds — what it would have
  got after the minutes anyway. A scene that can be arranged takes a few
  dozen; on the same four minutes the budget alone, before the reservation,
  refused 66 intervals of 2 283 and ran in 22.6 s.

🔴 A search with backtracking has to be measured on its failures, not on its
successes. Every scene in the fixtures arranges in a few attempts, and the
one that could not was found by an encode that never finished.

### And the programme that then decoded wrong, twice in four minutes

With the search bounded, four minutes of the same programme went through
`harletty` and came back with two lossless checks failed and two intervals of
elements off by up to 10 880 — small errors, an arithmetic that diverged
rather than a stream that broke. Disabling the matrices' steps made it exact,
and the restart said why: a moving coding matrix carried a **step on a source
whose coefficient was zero**. The stream names a matrix's sources by a mask of
its non-zero coefficients and carries a step for those alone, so that step was
never written and the decoder never applied it — while the encoder's own
arithmetic did. A weight that crosses zero inside the interval fits a line
through zero: an intercept of nothing and a slope that is not, and the dense
channels a fold leaves cross zero often enough to do it twice in four
minutes. It could have happened without folds at any time and did not,
measurably: the same four minutes fold-free are exact either way.

Two things, and a third that was only in the way:

- `aim_the_matrices` gives no step to a source without a coefficient.
- `Primitive::correction` applies no step to one either, whatever `delta`
  says, and the test's own forward decoder reads the steps the way the real
  one does — through the mask. A step on an absent coefficient is a test.
- The reader never read the immersive syntax's interpolation section, so
  every field of a block after a moving matrix was a bit out of place. It read
  as nothing while nothing moved, and as output shifts of −4 and −8 once
  something did, which is where this began — a decoder warning is the fact;
  what a reader shows next to it is a second question.

The four minutes decode byte for byte now, with and without folds, and every
presentation without a word from the decoder.

## Partitioning a unit into more blocks, and the header that stops it

An access unit is one block today, and two when it restarts. The format lets it
be several, each with its own codebook and width and the filter carried across
— which on a transient ought to let the loud half and the quiet half be coded
at their own widths instead of both at the loud one's.

It was priced before it was built, by coding every unit's tail both ways and
summing what the search says each costs. Residual bits only, before any block
header:

| fixture | one block | two halves | |
|---|---|---|---|
| real8 | 23 743 716 | 23 581 236 | **−0.684 %** |
| prog_stereo | 53 734 337 | 53 555 983 | −0.332 % |
| busy16 | 26 978 595 | 26 951 858 | −0.099 % |
| prog_71 | 138 965 843 | 138 858 668 | −0.077 % |
| prog_51 | 131 363 082 | 131 298 249 | −0.049 % |
| real16 | 27 169 894 | 27 641 877 | **+1.737 %** |

Then the header. An extra block costs, **per substream**: the bit that says a
block header follows, the bit that says it is not a restart, five bits of
decoding-parameter presence flags, one bit per channel the substream codes, and
the bit that says whether it is the last. Eight plus the channels — and the
block size itself is free in the steady state, since both halves are the same
length and only the first block after a change states one.

| fixture | saved | header | net on the stream |
|---|---|---|---|
| real8 | 162 480 bits | 12 000 × 24 = 288 000 | **+0.478 %** |
| prog_stereo | 178 354 | 48 500 × 10 = 485 000 | **+0.523 %** |
| busy16 | 26 737 | 4 800 × 48 = 230 400 | **+0.711 %** |
| prog_71 | 107 175 | 48 500 × 24 = 1 164 000 | **+0.714 %** |
| prog_51 | 64 833 | 48 500 × 22 = 1 067 000 | **+0.717 %** |
| real16 | −471 983 | 12 000 × 48 = 576 000 | **+3.451 %** |

Not taken, and not close: the header is three to ten times what the split
saves. Four and five blocks were not measured because they cannot rescue it —
they multiply the header by three and four while the residual saving is under
0.7 % of an already small number, and the fixture that loses before any header
is charged loses more the more blocks it is given.

The reason is the shape of the format rather than the shape of the audio: a
block header is charged **per substream**, so a sixteen-element stream pays it
four times, and a forty-sample access unit is short enough that adapting the
coding twice inside one buys very little. A stream whose access units were
longer — a higher rate factor doubles them — is the case where this would want
measuring again.

## Where the speed ended up

Encoder alone, release, best of three, one thread except where the `parallel`
feature is on — which `hz-cli` and `xtask` both turn on.

| fixture | full | fast |
|---|---|---|
| prog_mono, 1 ch | 1.256 s | 0.616 s |
| prog_stereo, 2 ch | 1.498 | 0.833 |
| prog_51, 6 ch | 1.939 | 1.222 |
| prog_71, 8 ch | 2.427 | 1.593 |
| prog16, 16 elements | 0.325 | 0.254 |
| real16, 16 elements | 0.928 | 0.680 |
| busy16, 16 elements | 0.473 | 0.339 |
| real8, 8 ch | 0.624 | 0.397 |

About 5 ms per channel-second of audio at full effort on a real programme in
sixteen elements, against 13.3 ms before any of this — so a two-hour
sixteen-element programme went from twenty-five minutes to under ten.

Where it came from, in order of what each was worth: not fitting a filter
nothing looks at (7 to 16 %), searching the channels of a unit at once (25 to
66 %, and the pool has to be sized to the channel count — 3.34 s against 1.86 s
on the 5.1 programme for the same work), the autocorrelation as contiguous dot
products (3 to 12 %), the filter histories as rings (6 %), finding the narrowest
field by halving (1 to 11 %), the candidate buffers as arrays rather than
allocations (1 to 11 %), and the bit writer emitting bytes rather than bits (0
to 2.5 %).

Two rate levers cost some of it back and are paid for in size: the fourth
second-filter design is a fourth trial per channel per restart, 8 to 14 % at
full effort, and matrices with more than one source cost 2 % on the
programmes and up to 11 % on the busiest sixteen-element fixture.

## What holding an interval bought, and the one thing it did not

The encoder used to write each access unit as it arrived, so every decision
that stands for a restart interval was made on the interval *before* it. It
holds one now. Three things followed, each measured on its own:

| | whole set | the programmes |
|---|---|---|
| Holding the interval, deciding nothing differently | 0 | 0 |
| Matrices fitted on the interval, with a line through the weight | −0.421 % | −0.002 % |
| The second filter decided on the interval it will meet | −0.053 % | −0.064 % |
| Tighter `max_shift` and `max_output_bits` | 0 | 0 |

−0.473 % over the set. The largest single number in it is **−2.64 % on the
sweeping fixture**, and it is worth saying why: a matrix that ramps states a
coefficient and a step, and fitting the whole interval at once gives the
*average* weight, which is half the drift away from where the ramp should
start. Fitted that way it cost **+1.05 %**; with a line through four slices of
the interval it is −2.64 %. The same lever, the wrong estimator.

The tighter declarations buy no bytes and were never going to: the fields are
fixed width. What they buy is a header that is true about its own interval, and
the reference decoder checks it.

**The Viterbi is not done.** The plan asks for the first filter to be chosen by
a dynamic program over the interval's blocks — state the filter in force,
transition the description bits when it changes — which would replace the
quarter share in `rate.rs` with the exact cost of the exact change. It is
worth doing and it is not a small change: the emission costs are only
path-independent while no second filter is in force (with one, a block's
residuals depend on the previous block's first filter through the residual
history), and running the program at all means choosing every coding in the
interval before writing any of it, against a second copy of the decoder model.
That second copy is the thing `crate::model` exists to have got rid of, so it
wants doing carefully rather than quickly. `max_huff_lsbs` would come with it.

## What the amortisation constant is worth, and why the cheap way to replace it fails

The plan's remaining WS4.3 item is a dynamic program over the interval's blocks
that replaces the quarter in `rate.rs` with the exact cost of the exact change.
Before building it, three measurements — and then the cheap version of it,
built and put down.

### How much there is to win

The whole budget a scheduler can touch on the description side is what filter

### So the Viterbi stays unbuilt, and this says what would change that

It is the only correct way to replace the constant: it optimises the total
rather than pricing by a proxy, which is exactly why the proxy failed. Against
that, it needs a second forward pass and a second decoder model — the thing
`crate::model` exists to have got rid of — and its emission costs are
path-independent only while no second filter is in force, which is not the
common case. The bound above says the prize on a programme is a couple of
tenths of a per cent and on `real16`-like material perhaps a quarter of one per
cent.

It is worth building the day one of two things is true: an encode of real
material shows the description share above about two per cent, or the second
filter is decided per block rather than per interval, which is the change that
would make the lattice path-dependent everywhere and force the exact treatment
anyway.

## Where the encode's time goes, and what four commits took off it

Measured on five minutes of a two-hour programme, sixteen objects and an LFE
folded into twelve elements — the shape a dubbing pipeline actually hands this.

The whole command is 92 % `hz-mlp`, 7 % the fold, 1 % reading. Inside `hz-mlp`,
comparing one thread against twelve told us where to look:

| phase | one thread | twelve | scaling |
|---|---|---|---|
| second filter | 68.0 s | 8.8 s | 7.7× |
| channel search | 34.7 s | 11.0 s | **3.2×** |
| matrix search | 3.3 s | 3.4 s | none |
| writing the units | 2.0 s | 3.0 s | none |

The channel search scaled badly for a reason that does not show up in a
profile's totals: it forked its channels and joined them again **once per
access unit**, 360 000 times over five minutes, for forty samples of work a
channel. The fork cost more than the work it scheduled — visible in the
totals as parallelising nearly doubling the CPU-seconds, 111 s to 215 s.

| | wall | CPU |
|---|---|---|
| before | 30.1 s | 783 % |
| matrix search across the destinations | 27.8 s | 783 % |
| the five second-filter trials side by side | 26.4 s | 825 % |
| the channel search forking once an interval | **20.1 s** | **642 %** |
| the pool sized to the machine | **17.4 s** | 955 % |

**1.73×, byte-identical** on the programme and on twelve fixtures. The third
step is the one to notice: the CPU went *down*, because it removed waste
rather than adding parallelism.

### Order mattered

Sizing the pool to the machine was tried before the fork moved out and made the
encode **21 % slower** — thirty-two threads to wake and collect per access unit
instead of twelve. The same change, after, is 13 % faster. A lever measured
once and put down is worth picking up again when what is under it has changed,
which is the same lesson `RESTART_INTERVAL` taught.

### What is left

Of 17.4 s: 5.1 s of second-filter search and 5.1 s of channel search, both
across the pool; then 3.7 s that is not — writing the units 2.2 s, preparing
them 1.2 s, gathering the interval 0.3 s.

**Writing will not parallelise the obvious way.** The residuals go out
interleaved sample by sample across a substream's channels — `for frame { for
channel }` in `write_block_data` — so there is no per-channel bit string to
encode apart and concatenate. Checked, not assumed.

**The fold now runs a span ahead**, on a thread of its own: 17.4 s to 16.6 s,
1.81× over the five steps. Less than the 11 % the phase timing suggested,
because the producer and the writer compete for the same cores instead of
taking turns — a phase's cost is what it takes *alone*, and hiding it behind
another only pays where there is a core idle to hide it in.

**And the second-filter search is the largest single thing at 5.1 s**, because
`pick_second` codes 44 blocks in each of five modes per channel per interval —
about 1.7 times the coding the interval itself needs. `--fast` is the lever
that already exists for it; anything else there is a rate decision, not a
speed-up's business.

## A third of the machine, and the margin that widening it found

With `--presentations` on, a thirty-two-thread machine sat at 30 % — the
search of the section before this one fixed, and the encoder back to about
what it was fold-free, which was never more than a third of the machine
either. `HZ_TIME=1` in the environment now makes the encoder time its phases
and print them when the stream is finished. On four minutes of a
twelve-element programme, the sixteen objects and LFE of a dubbing mix
clustered to twelve, with the folds on:

| phase | before | after | across the pool? |
|---|---|---|---|
| second-filter search | 4.5 s | 4.5 s | yes, per channel |
| channel search | 4.8 s | 4.8 s | yes, per channel |
| preparing the units | 2.5 s | 2.3 s | **now**, per unit |
| judging the matrices | 3.0 s | 0.65 s | **now**, per destination |
| building the presentations | 1.2 s | 1.2 s | no |
| writing the units | 1.7 s | 1.7 s | no |

| | wall | CPU |
|---|---|---|
| before | 25.6 s | 667 % |
| the matrices judged across the pool | 19.1 s | |
| the units prepared in passes | **17.0 s** | **1050 %** |
| fold-free, the same | 15.5 s | 1117 % |

**Judging the matrices** walked the destinations one after another on one
thread: for each, four units of the interval coded plain and coded against
each candidate. A destination's judgement reads the interval and the first
unit as they stand and writes nothing another destination reads, so they are
all judged at once and then admitted in substream order under the four-bit
budget, which is the one thing about them that is sequential. Byte-identical.

**Preparing the units** walked the 128 of them on one thread: each
de-interleaved through the permutation, certified, its dead bits taken off,
the cascade taken off, the matrices taken off — and before any of that the
interval was gathered a second time for the matrices to be suggested on, with
the cascade taken off twice. The units are independent except for one thing:
the shift a silent unit holds is the shift in force before it. So it is three
passes across the pool with a serial pass between the first two that takes no
time at all — measure and certify; resolve what the silent units inherit; the
dead bits and the cascade off; suggest and judge the matrices on the interval
gathered from that; the matrices off. The interval is gathered by transposing
a unit-major scratch buffer, 0.1 s, and the second gathering is gone.

### 🔴 And the fold-free stream came out 0.3 % larger

Which it should not have, since nothing about what was decided had moved —
except one thing had. The old judge priced the first trial unit's plain coding
on the *prepared* unit, dead bits off, and every candidate's matrixed coding on
the interval as gathered, dead bits on. A programme's elements are twenty bits
in twenty-four: four dead bits a sample, a hundred and sixty bits on that one
unit that the matrix had to make up before it was even level. A margin, never
written down, and once the judge priced both sides in one domain it was gone
and the stream grew. So the marginal matrices *lose*, and the margin is
worth having on purpose.

Measured as an explicit margin over the four trial units, on the fixture set
and on the four minutes of the programme:

| margin over the four trials | 0 | 40 | 80 | 160 | 320 |
|---|---|---|---|---|---|
| fixture set | 77 093 644 | −0.19 % | **−0.30 %** | −0.29 % | |
| prog_stereo | | −0.26 % | −0.61 % | −0.69 % | |
| prog_51 | | −0.49 % | −0.70 % | −0.72 % | |
| prog_71 | | −0.13 % | −0.29 % | −0.31 % | |
| prog16 | | −0.41 % | −0.76 % | −0.84 % | |
| busy16 | | −0.24 % | −0.45 % | −0.60 % | |
| sweep16 | | +0.18 % | +0.32 % | +0.51 % | |
| the programme, fold-free | 84 785 186 | −0.81 % | **−0.92 %** | −0.83 % | +0.18 % |
| the programme, carrying folds | 93 354 540 | −0.66 % | **−0.81 %** | −0.55 % | |

`MATRIX_MARGIN` is twenty bits a trial unit — half a bit a sample at the base
rate — which is eighty over the four. Every programme fixture is smaller, the
synthetic ones do not move, and the only fixture that grows is the sweep,
whose every matrix is genuine. Why a matrix that wins its trials narrowly loses
the interval: it was picked among a destination's candidates on four units of
a hundred and twenty-eight, so it is the candidate the sample favoured as much
as the one that is best, and the narrower its win the more of it is the
sample's. The margin is what that luck is worth. Against `main` the four
minutes are now 0.62 % smaller fold-free and 0.81 % smaller carrying folds,
both decoding bit-exactly to the elements and every presentation.

### What is left, and why it is a ceiling

Of 17.0 s, 15.9 s is the encoder's own. Three phases run across the pool and
are 12 s of it: the second-filter search, the channel search, and now the
matrices — and each forks **per channel**, which on twelve elements is twelve
threads of thirty-two. A channel's interval is walked in order, every block's
decision made against what the model holds after the one before, so splitting
a channel across threads is not a speed-up, it is a different stream.
Preparing forks per unit and does fill the machine. The 3 s that is on one
thread is building the presentations, 1.2 s, and writing the units, 1.7 s,
the latter for the reason the section before gave. So about 1050 % on this
material is where it stops short of changing what is written; more channels
would take more of the machine, and a stereo programme takes two threads of it.
